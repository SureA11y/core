# Known limitations

Stated plainly and upfront, not left for you to discover. Some items are design decisions, each with its reasoning. Others come from where a scan runs: jsdom, a browser, or the page's own scripts. Each says what a scan can't establish and, where there is one, what to do about it.

## What to do about them

| If… | Then… |
|---|---|
| Content appears only after a click, a hover or a data load | Bring the page to that state yourself, then scan it. Scan each state that matters. |
| A check needs layout: target size, text spacing, contrast against what is painted under text | Scan in a real browser. jsdom has no layout (the result's `engine.environment.layout` is `false`), so these rules measure less there or report `notApplicable`, as the sections below say. |
| A requirement is about keyboard operation, such as a keyboard trap | Test it with a keyboard. No scan covers it. |
| A result is `cantTell` | Read the occurrence's `uncertainty.code` and `uncertainty.needed`, and decide it by hand. |
| The page is responsive | Scan at each width you care about. |
| Two runs of the same page differ | Compare `engine.version` and `engine.environment` (viewport, fonts and images still loading), and reload the page between scans. |
| A scan reports no failures | That is not a conformance claim. See [`WCAG_CONFORMANCE.md`](./WCAG_CONFORMANCE.md). |

The sections below give the reasons.

## Outside what one scan can see

A scan reads the page at one moment, in one state, at one viewport: the DOM, its computed styles and, in a real browser, its layout. It does not use the page as a person does. It doesn't move through it with a keyboard, open its menus, wait for its data or resize it. (In a browser a few rules focus an element or add a style sheet for the time of their check, and put it back; see [In a real browser, some rules change the page](#environment-dependent--depends-on-how-you-run-it).) The items here need that kind of interaction over time, so another rule can't close them. They need an interaction test or a person:

- **Keyboard-trap detection** (WCAG 2.1.2) — requires driving focus around the page and watching where it lands, which no single read of the DOM can do. A technique that would work has been scoped out (see the keyboard-trap section of [`ACT_RULE_MAPPING.md`](./ACT_RULE_MAPPING.md#keyboard-trap-detection-scoping-notes)), but it would be this engine's first check to mutate the page it is inspecting, so it is not built and would not be part of a normal scan if it were. Nothing in static markup stands in for it in the meantime.
- **Reflow / clipping at zoom** (WCAG 1.4.10) — requires real layout measurement (`clientWidth`/`scrollWidth`) at a simulated 320px-equivalent viewport. Unlike some CSS-declaration-based heuristics elsewhere in this engine, there is no static markup proxy for "does content get clipped at 400% zoom" at all.
- **Dynamic/post-interaction state** — anything that only exists after a click, hover, or async data load (a modal's contents, a dropdown's options, form-validation error messages) is invisible to a scan of the page's *current* DOM. If your framework renders it eagerly (even off-screen/`hidden`), it's scannable; if it only exists after interaction, it isn't, unless you drive that interaction yourself before scanning (e.g. click the button, *then* scan). Scanning the opened state checks what is in it, not whether a keyboard or screen-reader user can open, use and close it.

## Environment-dependent — depends on how you run it

- **jsdom (Node, no real browser) has no CSS layout engine.** Rules needing real geometry — most notably `target-size-minimum` (WCAG 2.5.8, needs real `getBoundingClientRect()`) — report `notApplicable` under plain jsdom rather than guess. Run under a real browser (Puppeteer/Playwright — see [`INTEGRATION.md`](./INTEGRATION.md) Pattern 2) to get real findings from these rules.
- **Whether text wraps needs layout, so text-spacing findings on non-wrapping text are reported for review.** WCAG 1.4.12 and the ACT rules behind it apply only to text containing a soft wrap break, which a static scan cannot establish. `avoid-inline-spacing` treats text as wrapping by default, so an ordinary forced value below the metric still fails; where no wrap is possible for a reason that *is* visible without layout — text not allowed to wrap, or a fixed-width element inside a horizontally scrolling ancestor — it reports `cantTell` instead. Text that never wraps for some other reason is still reported as a failure.
- **The engine runs on the page's own JavaScript built-ins.** A page whose scripts break one it relies on (`Array.prototype.filter`, `Map`, `JSON.stringify`, `String.prototype.toLowerCase` and others) stops the scan with an error coded `PAGE_BUILTINS_BROKEN` that names each, rather than giving a result that reads well and is wrong; one broken before the bundle is injected (`Object.keys`) stops the bundle loading. A page that adds `then` to `Object.prototype` is scanned as any other. DOM methods a page replaces (`getComputedStyle`, `querySelectorAll`, `getBoundingClientRect`) are not checked: rules read what they return.
- **A name is not worked out from content nested more than 256 levels deep.** The walk stops there (Chrome gives no name from content 100 levels down), so a button or link whose only name is deeper is asked about (`name_contentTooDeep`) by `button-name-present` and `link-name-present`; other rules that name from content read such content as empty. A walk thousands of levels deep ran out of stack.
- **Content in a closed shadow root can't be read.** No script reaches inside `attachShadow({ mode: 'closed' })` or a declarative `shadowrootmode="closed"`, so the engine can't see what a browser names from there. `button-name-present` and `link-name-present`, and the menu item, option, tab, tree item, summary and tooltip name rules, ask about an element whose name could come from a custom element that renders but shows no readable content, instead of failing it. A closed root on a built-in element (a `<span>`) looks like an empty one, such as an icon drawn by CSS, so a button over one is still failed. Check what such a component exposes by hand, for example with a screen reader.
- **A name or state a custom element sets through `ElementInternals` can't be read.** `this.attachInternals().ariaLabel = 'Save'` names the element in every browser, but no script can read it back. Where a component keeps its internals on a property (`_internals`, `internals`, `internals_`, `__internals`), the engine reads them through it, and passes or fails the element by what they say. For any other defined custom element with no name (or no required state) the name rules and `aria-required-attr` ask (`name_internals`, `state_internals`) instead of failing; check those in the browser's accessibility tree, or install the opt-in internals hook (`internalsHookScript()`), which records every element's internals for the scan when it runs before the page's scripts, and then also tells an element that never attached any (see [`INTEGRATION.md`](./INTEGRATION.md#reading-private-elementinternals-the-internals-hook)). A role set only through internals is not seen at all, with the hook or without, so such an element is not checked for its role. Built-in elements, and custom elements that aren't defined, are judged as before.
- **A scan taken while a modal dialog is open sees the dialog, not the page.** A `<dialog>` opened with `showModal()` (or an open `<dialog aria-modal="true">`) makes the rest of the document inert, and browsers give assistive technology only the dialog. The engine follows that: content behind the dialog is left out of every rule, as other hidden content is, and the rules about the page's own structure (`page-has-heading-one`, `landmark-one-main`, `bypass-blocks-present`, `region`) report `notApplicable`, since the scan cannot see that structure. Scan the page again with the dialog closed to judge what is behind it. Two limits: a modal `<dialog>` inside a shadow root is not detected, and a custom modal built from a `role="dialog"` element with `inert` or `aria-hidden` on the rest of the page is handled only through those attributes, which hide the page but do not tell the structure rules a dialog is open. Other engines differ here: some do the same, others judge the page behind the dialog as if nothing were open.
- **`<dialog>` and other elements hidden by the default UA stylesheet** (no `open` attribute, `display: none` by spec), along with any other subtree hidden via `display:none`, `visibility:hidden`, `[hidden]`, or closed `<details>`, are **excluded from rule evaluation by default** — matching the visibility-aware behavior of other established engines. This is a deliberate default (`engineOptions.includeHiddenElements: false`), not an oversight: hidden content isn't reachable by assistive technology or keyboard until it's shown, so flagging a markup defect inside it by default would often be noise. Set `engineOptions.includeHiddenElements: true` to evaluate hidden/collapsed subtrees anyway — e.g. to catch a markup defect (like a broken ARIA ID reference) before a dialog ever opens. See [`ENGINE_OPTIONS.md`](./ENGINE_OPTIONS.md#engineoptions--the-rest) for the option and exactly which hiding mechanisms it covers.
- **jsdom has no popovers.** It ships HTML's rule hiding a closed `[popover]`, but no `showPopover()`, and reads `:popover-open` inconsistently. Where the DOM has no `showPopover`, the engine treats every `[popover]` other than an open `<dialog>` as closed and hidden, so its content is not checked; a popover the page's own CSS keeps visible is not checked under jsdom either. In a browser the engine reads what is displayed. To check a popover's content, scan the page in a browser with the popover open.
- **jsdom keeps a font size as written.** A browser reports a computed font size in px; jsdom keeps a keyword or a `calc()` as written. The engine reads the keywords at a browser's sizes for a 16px default (`xx-large` is 32px) and `calc()` of lengths and numbers, so large text is told apart as in a browser. `larger` and `smaller`, which depend on the parent's size, are not resolved under jsdom: such text is held to the normal-text ratio, and its message gives its size as 0px. A browser resolves both.
- **jsdom's computed `text-shadow` is unreliable on a second read of the same element.** Confirmed in jsdom 29.1.1: reading a computed `text-shadow` value a second time on the same element — through any accessor, from any freshly-requested `CSSStyleDeclaration` for that element, regardless of caching — silently returns a different, wrong "no shadow" value instead of the real declared one. The first read is always correct. This engine works around it internally by reading each element's `text-shadow` exactly once per run and caching the result (see `__textShadowInfoEl` in `src/core/contrast-helpers.js`), so a single scan is unaffected. It only surfaces if you read `getComputedStyle(el).textShadow` yourself, more than once, against the same jsdom-parsed element — a real browser has no such bug.
- **A second scan of the same jsdom DOM can lose a style that overrides a shorthand.** jsdom keeps an element's computed style once read, until the DOM next changes, and the copy it gives back from that cache loses a longhand that overrides a shorthand from a less specific rule: with `*{background:#888}` and `style="background-image:url(hero.png)"`, the first read gives the image and every later one `none` (`background-color` over `background` and `font-weight` over `font` do the same). A scan keeps the style it read first, so it is unaffected, but a second scan of the same unchanged DOM can miss the image and pass text the first asked about (`contrast-computable`). Scan a fresh parse, or change the DOM between scans, which clears jsdom's cache. `@surea11y/core/testing` does this for its second, Node, scan: `runa11yCoreOnHtml` gives it a parse of its own, and `runa11yCoreOnDom` adds a rule that matches nothing to a style sheet and removes it first. A real browser has no such bug.
- **Under jsdom, scan time grows with the square of DOM depth, not with element count.** jsdom resolves inherited CSS by walking an element's ancestor chain on every `getComputedStyle` call, so one call per element costs O(elements x depth). Measured on jsdom 29.1.1 with no engine code involved: 4000 elements in one chain take 8.3s of `getComputedStyle` alone, against 0.25s for the same 4000 as siblings. The engine's own ancestor walks are capped and stay linear, so this is jsdom's cost rather than the rules'. It affects `runDomRulesInPage` and anything built on it, including `@surea11y/test-matchers`; a real browser computes inherited style natively and does not have this shape. Component frameworks routinely nest 100-300 deep, which is comfortably fast — it becomes noticeable past roughly 1000.
- **A layout is measured at one viewport, with the fonts the page has at that moment.** Rules that measure what the browser draws, `text-spacing-content-loss`, `target-size-minimum` and `skip-link`, hold for the viewport the page was scanned at: a responsive page can cut text off, or shrink a target, at one width and not at another, and text measured before its web font loads is a different width. The result records both in `engine.environment`, and the findings of those rules repeat their viewport and say what was measured (how far text went past the edge, how big a target is and how close its neighbour), so a finding that differs between runs can be traced to the conditions. Scan at each width you care about, and wait for the page to settle before scanning: `waitForPageReady()` waits for the load event, web fonts and images (see [`INTEGRATION.md`](./INTEGRATION.md#waiting-for-the-page-before-a-scan)), and the result records in `engine.environment` whether fonts or images were still loading.
- **Under jsdom, scan time also grows with the size of the stylesheet.** jsdom computes a style by matching every CSS rule against the element, and it keeps the results only until the next change to the DOM. The engine doesn't change the DOM during a scan, so each element is computed once, but that once costs O(rules): on a frozen Daily Mail page (7,916 elements, 2,683 CSS rules, jsdom 29.1.1), the first computation of 5,735 elements takes about 224 s of a 243 s scan, at some 39 ms each. That is jsdom's cost; a real browser computes the same page in a fraction of a second. jsdom also leaves custom properties unsubstituted, so a color set with `var()` is unreadable there: the text or background is asked about (`contrast-computable`) rather than measured. Run a real browser (see [`INTEGRATION.md`](./INTEGRATION.md) Pattern 2) for large production pages.
- **In a browser, contrast is measured against what is painted under the text, as the page is at that moment.** Text over an image, a gradient, or paint covering only part of it is asked about (`contrast-computable`, reason code `BACKGROUND_OVERLAP`) rather than measured. Text that a box with `overflow: hidden` keeps wholly out of view, such as a carousel slide off its track, is left out until it is in view, so scan the page in that state to check it. Fixed and sticky boxes over text are ignored. Under jsdom, text is measured against its ancestors alone. How the measurement works: [Contrast](./LAYOUT_MEASUREMENT.md#contrast).
- **Generated text is measured only in a browser, and only where it can be read.** The text a `::before` or `::after` `content` writes and a list item's `::marker` are measured in the pseudo-element's color and font; content that can't be read (a counter in a page's own `@counter-style`), and a `::before` or `::after` positioned out of the flow with no background of its own, are asked about (`contrast-computable`) instead. Markers are looked for only on `<li>`. Under jsdom, which computes no pseudo-element styles, generated text is left out. Details: [Contrast](./LAYOUT_MEASUREMENT.md#contrast).
- **A form field's text and placeholder are measured as the field draws them, with gaps.** The text a browser draws in an empty date or time field, and a file input's button and file name, are not measured. A drop-down `<select>` is measured as the closed control draws it, its shown option in the select's own colors; another of its options with colors of its own is shown only in the list the platform draws when it opens, and is `cantTell` (`SELECT_OPTION_COLOR`). A placeholder below its ratio is `cantTell` (`PLACEHOLDER_BELOW_THRESHOLD`) rather than a fail, and under jsdom placeholders are not measured at all. Details: [Form fields](./LAYOUT_MEASUREMENT.md#form-fields).
- **`target-size-minimum` works the hit region out from the layout rather than by hit-testing.** Targets below the fold or in a scrolling box are measured whole, as if scrolled into view; fixed and sticky boxes over a target are ignored; 3D transforms, most `clip-path` shapes and an ancestor's rounded clipping are measured as a bounding box; and links between separators alone ("Edit | Delete") that crowd each other are asked about rather than exempted. Under jsdom the rule is `notApplicable`. Details: [Target size](./LAYOUT_MEASUREMENT.md#target-size).
- **Contrast is computed in sRGB.** Colors given in `oklch()`, `oklab()`, `lab()`, `lch()` or `color()` (the computed form of `color-mix()` and relative colors too) are converted to sRGB, as a standard display shows them; one outside sRGB, such as a saturated `display-p3` red, is clipped to its edge, which is what Chromium draws on an sRGB screen. A wide-gamut screen can show that color more saturated than the ratio assumes. A background color the engine cannot convert, a `color()` in a space it does not know, is not treated as transparent: `contrast-computable` asks about the text with reason code `BACKGROUND_UNPARSABLE`, and the other contrast rules leave it out.
- **In a real browser, some rules change the page for the time of their check, and the page's own scripts can react.** To measure what the browser draws, `css-hidden-focus` focuses elements as the keyboard would, and switches transitions off on the element it measures; `aria-hidden-focus` focuses an element inside an `aria-hidden` subtree to see whether the page moves focus away at once (a focus-trap sentinel); `text-spacing-content-loss` adds a style sheet with the WCAG 1.4.12 spacing. All of this is put back before the rule returns: focus, scroll position, style attributes and the added style sheet. What cannot be put back is what the page's scripts do in response, since focusing an element fires its `focus` and `focusin` handlers: a carousel may move to the focused slide, moving `aria-hidden` with it, or enable a button. The findings of that scan are those of the page as it was found: `aria-hidden-focus` reads which subtrees are hidden, and the markup it reports, before it focuses anything. But the page is left as its scripts made it, so a second scan of the same page can find something else: if you scan a page you go on using, or scan one page twice, reload it in between.
- **Static markup vs. live/post-hydration DOM state.** The rule logic itself is DOM-source-agnostic — it evaluates whatever DOM it's handed, whether that's jsdom-parsed static HTML (Pattern 1) or an already-loaded, already-hydrated real browser tab (Pattern 2, see [`INTEGRATION.md`](./INTEGRATION.md)). But the CLI (`npx @surea11y/cli scan <url>`) specifically fetches static HTML only, with no JS execution — see [the CLI docs](https://github.com/SureA11y/cli/blob/main/docs/CLI.md). For a JS-framework-hydrated widget whose server-rendered markup intentionally ships one state before client JS syncs it (e.g. `<input type="checkbox" aria-checked="true">` shipped before client JS sets the native `checked` property to match on hydration — an extremely common, entirely legitimate pattern), a CLI scan only sees the pre-hydration markup. A scan running inside an actual loaded browser tab sees the post-hydration state instead, so the two can disagree on exactly this class of element for reasons that have nothing to do with rule correctness. That's why `aria-checked-state-mismatch` is capped at `manual`/`cantTell` rather than a hard `fail`. If you need live-DOM accuracy for hydration-sensitive checks, run the library directly against an already-loaded page via Pattern 2, not the static-fetch CLI.

## Not attempted: judgment calls that aren't automatable safely

These have no comparably safe heuristic at this engine's bar (`fail` must stay reserved for deterministic violations, full stop). Building them anyway would either catch almost nothing (too narrow to be useful) or risk real false positives (too broad to trust):

- **"Is this heading/label text meaningful?"** — real headings and labels are enormously varied and legitimately short ("FAQ," "Name," "Overview" are all fine), so nothing decides from markup whether a heading describes the section under it or a label describes the field beside it. What *is* decidable is that some strings cannot describe anything: `heading-quality` and `form-control-label-quality` flag leftover placeholders, numbered template slots, filenames and URLs against curated exact-match lists, the same precision-over-recall trade-off `link-name-quality` makes. Both are `manual` rules capped at `cantTell` — they raise a candidate for review, they never assert the text is wrong.
- **"Does this error message describe the problem?"** — what triggers a validation error and its content are almost always JS/validation-library-driven, invisible to a static scan in the first place; not just a heuristic-design problem.
- **Fine-grained time-based-media sub-checks** (WCAG 1.2.x has ~8 distinct ACT-rule-level cases beyond what's built) — audio/video content itself is fundamentally unverifiable from static markup; the two broadest, safest cases are covered (`media-alternative-transcript-evidence`, `video-caption`), the narrower ones are not, by design.
- **Images-of-text content analysis** (WCAG 1.4.5/1.4.9) — would need OCR-equivalent image understanding; out of scope for a static-markup engine.
- **Motion-actuation controls** (WCAG 2.5.4) — niche, low real-world incidence; not prioritized, not structurally impossible.
- **`img-alt-decorative`'s two ACT e88epe edge cases** — an `<img>` whose current network request state isn't "completely available" (still loading, or broken), and a `<canvas>` that is fully transparent (nothing actually drawn on it), are both exempt from ACT's own applicability. Neither is decidable from a static DOM scan (no image decoding, no canvas pixel readback), so both are left in scope rather than exempted — a rare false positive a human reviewer dismisses at a glance, safer than silently under-reporting a real excluded/undecorative element.

## What this means in practice

Most of the above is not unique to surea11y. Any tool that judges one state of the DOM shares the limits in [Outside what one scan can see](#outside-what-one-scan-can-see), and most automated tools leave the judgment calls to a person too, though tools differ in how they run, what they check, and how they report what they can't decide. The reason to state it explicitly here: a `pass` from this engine (or any automated tool) is never a substitute for the manual review WCAG itself requires for the criteria above. See [`WCAG_CONFORMANCE.md`](./WCAG_CONFORMANCE.md) for exactly what a `pass`/composite `pass` does and doesn't claim.
