# __PACKAGE__

__TITLE__: an accessibility standard for [`@surea11y/core`](https://github.com/SureA11y/core), as a pack. It has requirements of its own; core's rules and the pack's check them, and each requirement is a result of its own under the standard's profiles.

Generated by `surea11y-pack new`. Everything below works as generated: change it to your standard step by step, running `npm test` as you go. Core's guide to packs, [`docs/PACKS.md`](https://github.com/SureA11y/core/blob/main/docs/PACKS.md), explains each step in more depth.

## Start

```sh
npm install
npx playwright install chromium   # once, for npm run docs
npm test                          # the pack's tests, in jsdom
npm run lint                      # its rules against core's lint rules
npm run docs                      # docs/RULE_CATALOG.md, and the examples run in Chromium
```

## The requirements and the rules that check them

`requirements.js` holds the standard's requirements, per version: a number, its wording, and the WCAG criteria it corresponds to (`[]` for one WCAG doesn't make). `rule-map.js` says which requirements each rule checks: core's rules (by their ids in core's [`docs/RULE_CATALOG.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_CATALOG.md)) and the pack's, each with a `note` saying why.

From the two, `ruleMappedStandard()` (in `index.js`) gives the engine:

- **a result per requirement**, a rollup with the id `__NAMESPACE__-<version>-<requirement>`, which fails when one of its rules fails, asks (`cantTell`) when one asks, and passes when they pass. The HTML report shows them in a section of their own, and SARIF and JUnit tag them. A requirement its rules don't check in full says `partial: true` in `requirements.js`: its result is then `cantTell` where they all pass or are all not applicable, as a WCAG criterion's is. A standard whose requirements restate WCAG criteria one for one passes `applicability: 'wcag'` to `ruleMappedStandard()`, and each result agrees with WCAG's for its criteria ([below](#how-a-person-assesses-each-requirement) for their procedures);
- **the requirements each result names**: a rule's result lists its requirements in `meta.normativeMappings`, under a profile of the standard or with `engineOptions.mappings: ['__NAMESPACE__']`;
- **findings filed by reason code**: a row's `reasonCodes: { [code]: { requirements, outcome } }` sends a rule's findings of that code to other requirements (`[]` for none), or makes them questions there (`outcome: 'cantTell'`); the requirement's rollup then judges the rule by the findings that count toward it (core's [`PACKS.md`](https://github.com/SureA11y/core/blob/main/docs/PACKS.md#5-group-results-checklist-items-or-requirements));
- **findings filed by what they record**: a row's `findings: [{ when, requirements, outcome }]` sends a finding whose `data.details` fields equal those `when` gives (`{ 'typography.isLargeText': true }`) to those requirements, before its reason code: a standard can file contrast failures under the test for their text size;
- **checks of the tables**, run when the pack is prepared: a rule the engine doesn't have, a requirement the version doesn't have, or a WCAG criterion the WCAG version doesn't have makes the pack invalid, and the scan says why in `skippedPacks`.

## How a person assesses each requirement

`procedures.js` says, for each requirement of each version, how a person assesses it by hand, with no scan or after one: `proceduresFor('3', { packs: [pack], standard: '__NAMESPACE__' })` gives it, with the requirement's number and the standard's name, for a manual review, a conformance report or the requirements the rules leave open. Each requirement takes one of three forms, all in the generated file:

- `{ wcag: '1.1.1' }` (requirements 1, 2 and 4): it restates a WCAG criterion and takes that criterion's procedures from core, in every language core has them.
- `{ wcag: '2.4.2', replace: { 'page-title-descriptive': { ... } } }` (requirement 6): it restates a criterion but tests some of it its own way. The facet named shows the pack's steps instead of core's when the requirement is read; read as WCAG 2.4.2, the criterion stays core's. A criterion's facets and their ids are in `proceduresFor('2.4.2').facets`.
- `{ facets: [{ id, label, automation, tools, steps, passWhen, failWhen }] }` (requirements 3 and 5): a requirement of its own, with the test objectives a person checks.

Write the steps for the whole page, for someone without accessibility training, in English: one to eight short steps in a browser, then what they see if it passes (`passWhen`) and if it fails (`failWhen`, naming the requirement). `tools` lists what they need besides a browser: `keyboard`, `pointer`, `screen-reader`, `zoom`, `contrast-theme`, `devtools`.

A rule of the pack that tests a facet of a requirement of its own can claim it in `meta.coverage.facetsByRequirement` (`{ '3': ['new-window-warned'] }`); the requirement's procedures then list the rule, and its `meta.review` steps, under that facet. A standard whose requirements all restate WCAG criteria one for one can instead pass `applicability: 'wcag'` to `ruleMappedStandard()` and use the `procedures` it returns. Core's [`docs/PACKS.md`](https://github.com/SureA11y/core/blob/main/docs/PACKS.md#how-a-person-assesses-it-procedures) explains each form, and what `definePack` checks.

## The profiles: which rules run

A scan runs the pack's rules only under one of the standard's profiles (or when it asks for a rule by id). Each profile in `index.js` says what runs:

- `version`: the standard's version it targets.
- `mappedRules: true`: every rule `rule-map.js` lists for that version.
- `tags`: the rules carrying any of these tags. `wcagTagsOf('1.0')` gives the tags of core's WCAG A and AA rules for the WCAG version the standard's version is built on. Keep the namespace tag, `__NAMESPACE__`, so the pack's own rules run.
- `rules`: rules added by id, core's or the pack's, such as core's best-practice rules (`region`), which no WCAG tag selects.
- `exclude: { rules, criteria }`: rules left out, or WCAG criteria waived (their rollups go, and each rule whose every criterion is waived; a rule that also checks a kept criterion still runs). A rule the standard maps can't be left out.
- `severity`: another severity for a rule under the profile. Results show it, and keep the rule's own as `ruleSeverity`.
- `wcagVersion`: the WCAG version the profile's scans are judged by. A profile with WCAG tags takes it from them; one without, such as `__NAMESPACE__-1.0`, names it, here from `requirements.js`. Judged by 2.1, a scan reports no 2.2 criterion, such as 2.5.8.
- `keepsParsing: true`: the standard still requires 4.1.1 Parsing as written. Without it `duplicate-id` asks instead of failing, under any WCAG version: 2.2 removed 4.1.1, and the 2023 errata to 2.0 and 2.1 count it as satisfied.

As generated:

| Profile | Runs |
|---|---|
| `__NAMESPACE__-1.0` | Exactly the rules `rule-map.js` lists, the pack's own included, judged by the WCAG version `requirements.js` gives version 1.0; `img-alt-present` is critical. |
| `__NAMESPACE__-1.0-wcag` | Those, core's WCAG 2.2 A and AA rules, and `region`; not core's `contrast-minimum` (the 7:1 variant replaces it). |

After `npm run docs`, this pack's `docs/RULE_CATALOG.md` lists its rules, profiles and requirements.

## Add a requirement

1. Add it to `requirements.js` under each version that has it, with its WCAG criteria.
2. Map the rules that check it in `rule-map.js`: a core rule, or one of the pack's (see below).
3. Say how a person assesses it in `procedures.js`, under each version that has it.
4. Run `npm test`: the pack is checked as it is prepared, and `tests/profiles.test.js` lists the requirements' results.

A new version of the standard is a new entry in `VERSIONS`, its requirements, its rule map and its procedures, and a profile for it.

## Add a rule

1. Copy the rule closest to what you need, in `rules/automatic/` (it can fail) or `rules/manual/` (it asks a person). Name the file and the `id` `__NAMESPACE__-<what it checks>`.
2. Write its header: `@applicability` (what it applies to), `@expectation` (what it checks), `@reports` (what a finding carries). `npm run docs` puts them in the catalog.
3. Write `runInPage(ctx)`. It runs in the page, so it uses only `ctx`: `ctx.document`, and `ctx.helpers` for core's helpers ([`docs/RULE_HELPERS.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_HELPERS.md)). Read DOM properties through `ctx.helpers.dom` (`npm run lint` says where). Return `pass`, `fail` (automatic rules), `cantTell` or `notApplicable`, with an occurrence per element from `helpers.reportOccurrence`.
   - For core's rule at other thresholds, write a variant instead: `from` names the core rule, `config` its settings.
   - Give each finding a `reasonCode` in `data.details`, list the codes in `meta.reasonCodes`, and, for each code the rule asks about (`cantTell`), say in `meta.review` how a person answers it: a few `steps` from the element the finding names, then `passWhen` and `failWhen`, in English. Reports show them as "How to check", as for `__NAMESPACE__-new-window-review`.
4. Give it the `__NAMESPACE__` tag, list it in `rules` in `index.js`, and map it to the requirements it checks in `rule-map.js`.
5. Add its messages to `i18n/en.json`: the keys in its `meta.i18n` and its occurrences' `i18n`.
6. Add a test in `tests/rules/` and examples in `docs/RULE_EXAMPLES.md`, then run `npm test`, `npm run lint` and `npm run docs`.

Core's [`docs/RULE_AUTHORING.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_AUTHORING.md) describes a rule's fields and outcomes in full.

## Another language

Add `i18n/<locale>.json` with the same keys, and list it in `dictionaries` in `index.js` (`{ en: require('./i18n/en.json'), fr: require('./i18n/fr.json') }`). A scan with `engineOptions.locale: 'fr'` shows them; a locale with no dictionary shows English.

## Use it

In Node:

```js
const { runDomRulesInPage } = require('@surea11y/core');
const standard = require('__PACKAGE__');

const result = runDomRulesInPage(url, null, { packs: [standard], profile: '__NAMESPACE__-1.0' });
```

From the command line: `surea11y scan <url> --pack __PACKAGE__ --profile __NAMESPACE__-1.0`.

With a browser binding (Playwright, Puppeteer, Selenium, WebdriverIO), which registers the pack in the page for you:

```js
const result = await new A11yCoreBuilder({ page })
  .withPacks(standard)
  .options({ profile: '__NAMESPACE__-1.0' })
  .analyze();
```

In Cypress, `withPacks()` takes the module name (`'__PACKAGE__'`) and the binding's plugin prepares it in Node. In a page of your own, inject `packScript([standard])` from `@surea11y/core/pack` after core's browser bundle, or, for a `<script>` tag or an extension, ship one file built with `buildBrowserBundle({ packs: [standard] })`, and name the pack in `engineOptions.packs` as `__PACKAGE__@<version>`. The script runs only with the core that wrote it: build it again when you update core or the pack. See "Packs" in core's [`docs/ENGINE_OPTIONS.md`](https://github.com/SureA11y/core/blob/main/docs/ENGINE_OPTIONS.md#packs--rules-and-standards-from-outside-core).

## Publish

The package is `private`. Choose its licence, set `license` and remove `private` in `package.json`, and run `npm publish`. `core` in `index.js` says which core versions it works with; a scan with another core skips the pack and says why in `skippedPacks`.
