# __PACKAGE__

__TITLE__: an accessibility standard for [`@surea11y/core`](https://github.com/SureA11y/core), as a pack. It has requirements of its own; core's rules and the pack's check them, and each requirement is a result of its own under the standard's profiles.

Generated by `surea11y-pack new`. Everything below works as generated: change it to your standard step by step, running `npm test` as you go. Core's guide to packs, [`docs/PACKS.md`](https://github.com/SureA11y/core/blob/main/docs/PACKS.md), explains each step in more depth.

## Start

```sh
npm install
npx playwright install chromium   # once, for npm run docs
npm test                          # the pack's tests, in jsdom
npm run lint                      # its rules against core's lint rules
npm run docs                      # docs/RULE_CATALOG.md, and the examples run in Chromium
```

| `rule-map.js` | Which requirements each rule checks, core's rules and the pack's, with the reason. |
| `rules/automatic/__NAMESPACE__-link-text-specific.js` | A rule of its own that decides: links named only "click here" or "read more" fail. Uses core's helpers to find links and compute their names. |

## The requirements and the rules that check them

`requirements.js` holds the standard's requirements, per version: a number, its wording, and the WCAG criteria it corresponds to (`[]` for one WCAG doesn't make). `rule-map.js` says which requirements each rule checks: core's rules (by their ids in core's [`docs/RULE_CATALOG.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_CATALOG.md)) and the pack's, each with a `note` saying why.

From the two, `ruleMappedStandard()` (in `index.js`) gives the engine:

- **a result per requirement**, a rollup with the id `__NAMESPACE__-<version>-<requirement>`, which fails when one of its rules fails, asks (`cantTell`) when one asks, and passes when they pass. The HTML report shows them in a section of their own, and SARIF and JUnit tag them;
- **the requirements each result names**: a rule's result lists its requirements in `meta.normativeMappings`, under a profile of the standard or with `engineOptions.mappings: ['__NAMESPACE__']`;
- **checks of the tables**, run when the pack is prepared: a rule the engine doesn't have, a requirement the version doesn't have, or a WCAG criterion the WCAG version doesn't have makes the pack invalid, and the scan says why in `skippedPacks`.

## The profiles: which rules run

A scan runs the pack's rules only under one of the standard's profiles (or when it asks for a rule by id). Each profile in `index.js` says what runs:

- `version`: the standard's version it targets.
- `mappedRules: true`: every rule `rule-map.js` lists for that version.
- `tags`: the rules carrying any of these tags. `wcagTagsOf('1.0')` gives the tags of core's WCAG A and AA rules for the WCAG version the standard's version is built on. Keep the namespace tag, `__NAMESPACE__`, so the pack's own rules run.
- `rules`: rules added by id, core's or the pack's, such as core's best-practice rules (`region`), which no WCAG tag selects.
- `exclude: { rules, criteria }`: rules left out, or WCAG criteria waived (their rules and rollups go). A rule the standard maps can't be left out.
- `severity`: another severity for a rule under the profile. Results show it, and keep the rule's own as `ruleSeverity`.

As generated:

| Profile | Runs |
|---|---|
| `__NAMESPACE__-1.0` | Exactly the rules `rule-map.js` lists, the pack's own included; `img-alt-present` is critical. |
| `__NAMESPACE__-1.0-wcag` | Those, core's WCAG 2.2 A and AA rules, and `region`; not core's `contrast-minimum` (the 7:1 variant replaces it). |

After `npm run docs`, this pack's `docs/RULE_CATALOG.md` lists its rules, profiles and requirements.

## Add a requirement

1. Add it to `requirements.js` under each version that has it, with its WCAG criteria.
2. Map the rules that check it in `rule-map.js`: a core rule, or one of the pack's (see below).
3. Run `npm test`: the pack is checked as it is prepared, and `tests/profiles.test.js` lists the requirements' results.

A new version of the standard is a new entry in `VERSIONS`, its requirements and its rule map, and a profile for it.

## Add a rule

1. Copy the rule closest to what you need, in `rules/automatic/` (it can fail) or `rules/manual/` (it asks a person). Name the file and the `id` `__NAMESPACE__-<what it checks>`.
2. Write its header: `@applicability` (what it applies to), `@expectation` (what it checks), `@reports` (what a finding carries). `npm run docs` puts them in the catalog.
3. Write `runInPage(ctx)`. It runs in the page, so it uses only `ctx`: `ctx.document`, and `ctx.helpers` for core's helpers ([`docs/RULE_HELPERS.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_HELPERS.md)). Read DOM properties through `ctx.helpers.dom` (`npm run lint` says where). Return `pass`, `fail` (automatic rules), `cantTell` or `notApplicable`, with an occurrence per element from `helpers.reportOccurrence`.
   - For core's rule at other thresholds, write a variant instead: `from` names the core rule, `config` its settings.
4. Give it the `__NAMESPACE__` tag, list it in `rules` in `index.js`, and map it to the requirements it checks in `rule-map.js`.
5. Add its messages to `i18n/en.json`: the keys in its `meta.i18n` and its occurrences' `i18n`.
6. Add a test in `tests/rules/` and examples in `docs/RULE_EXAMPLES.md`, then run `npm test`, `npm run lint` and `npm run docs`.

Core's [`docs/RULE_AUTHORING.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_AUTHORING.md) describes a rule's fields and outcomes in full.

## Another language

Add `i18n/<locale>.json` with the same keys, and list it in `dictionaries` in `index.js` (`{ en: require('./i18n/en.json'), fr: require('./i18n/fr.json') }`). A scan with `engineOptions.locale: 'fr'` shows them; a locale with no dictionary shows English.

## Use it

In Node:

```js
const { runDomRulesInPage } = require('@surea11y/core');
const standard = require('__PACKAGE__');

const result = runDomRulesInPage(url, null, { packs: [standard], profile: '__NAMESPACE__-1.0' });
```

From the command line: `surea11y scan <url> --pack __PACKAGE__ --profile __NAMESPACE__-1.0`.

With a browser binding (Playwright, Puppeteer, Selenium, WebdriverIO), which registers the pack in the page for you:

```js
const result = await new A11yCoreBuilder({ page })
  .withPacks(standard)
  .options({ profile: '__NAMESPACE__-1.0' })
  .analyze();
```

In Cypress, `withPacks()` takes the module name (`'__PACKAGE__'`) and the binding's plugin prepares it in Node. In a page of your own, inject `packScript([standard])` from `@surea11y/core/pack` after core's browser bundle and name the pack in `engineOptions.packs` as `__PACKAGE__@<version>`. See "Packs" in core's [`docs/ENGINE_OPTIONS.md`](https://github.com/SureA11y/core/blob/main/docs/ENGINE_OPTIONS.md#packs--rules-and-standards-from-outside-core).

## Publish

The package is `private`. Choose its licence, set `license` and remove `private` in `package.json`, and run `npm publish`. `core` in `index.js` says which core versions it works with; a scan with another core skips the pack and says why in `skippedPacks`.
