# __PACKAGE__

__TITLE__: an accessibility standard for [`@surea11y/core`](https://github.com/SureA11y/core), as a pack, built on [`__BASE__`](https://www.npmjs.com/package/__BASE__). It takes the base's requirements, tests and rule map, changes them where it differs, and runs the base pack's rules: a scan passes both packs.

Generated by `surea11y-pack new --kind derived`. As generated, it is the base as it is: change it to your standard step by step, running `npm test` as you go. Core's guide to packs, [`docs/PACKS.md`](https://github.com/SureA11y/core/blob/main/docs/PACKS.md), explains each step in more depth ("A standard built on others", "A pack built on another pack").

## Start

```sh
npm install
npm test        # the pack's tests, in jsdom
```

## Use

```js
const base = require('__BASE__');
const pack = require('__PACKAGE__');

const engineOptions = { packs: [base, pack], profile: '__NAMESPACE__-1.0' };
```

A scan without the base pack, or with another version of it than the one this pack was made with, skips this pack and says why in `skippedPacks`.

## What is here

| File | What it is |
|---|---|
| `index.js` | The pack: its name, namespace, the packs it builds on (`uses`) and the standard. |
| `standard-data.js` | The standard, derived from the base's data (`deriveStandard`): its versions, requirements, tests, rule map and profile. |
| `tests/standard.test.js` | That the data is valid, that every rule-map row this standard doesn't change is the base's, that the profile runs with the base and is skipped without it; and a page for each change. |
| `eslint.config.js` | Core's lint rules, for rules you add. |
| `package.json` | The package: `private`, with the base as a dependency and core as a peer dependency. |

## Making it your standard

1. **The requirements and tests.** In `standard-data.js`, each requirement is based on the base's of the same id (`basedOn`) and takes its fields and tests. Give one fields of its own where your standard words it differently (`title`, `wcagSc`, `tests`), leave out those it doesn't have, and add your own without `basedOn`. A test is the same: `basedOn` the base's, or your own.
2. **The rule map.** It comes from the base through `basedOn`: a base rule linked to a requirement is linked to yours based on it. Where your standard asks something different, `OWN_ROWS` changes it: a row of your own replaces the base's for that rule, and `null` drops it. Read what the rule does before deciding: its row note in the base, its source, and core's [`docs/RULE_CATALOG.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_CATALOG.md) for core's rules. A link that could fail a page your standard accepts is dropped, or made a question (`outcome: 'cantTell'`).
3. **A page for each change.** In `tests/standard.test.js`, a page the base's row would get wrong, and the result your standard gives. The test that unchanged rows are the base's catches a base that changes under you.
4. **The profile.** It runs the rules the map links to a requirement, the base pack's and core's. It can name the law it is used for: `laws` beside `profiles`, and `law` on the profile, with the law's name, jurisdiction and official link only.
5. **Texts.** The standard's language is the base's (`lang`). A text you take from the base keeps the base's translations; one you reword takes yours, in `texts` (core's [`docs/PACKS.md`](https://github.com/SureA11y/core/blob/main/docs/PACKS.md), "A standard as data").

## Versions

Standard data, derivation and `uses` are experimental in core: a later minor may change them, so `core` in `index.js` and the peer dependency take no later minor (`__CORE__`). The base is a dependency at the version this pack was made with: a scan needs the same version of it in its packs.
