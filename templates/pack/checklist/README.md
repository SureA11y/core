# __PACKAGE__

__TITLE__: an accessibility checklist for [`@surea11y/core`](https://github.com/SureA11y/core), as a pack. It runs core's rules and its own under its profiles, and reports the checklist's items as results of their own.

Generated by `surea11y-pack new`. Everything below works as generated: change it to your policy step by step, running `npm test` as you go. Core's guide to packs, [`docs/PACKS.md`](https://github.com/SureA11y/core/blob/main/docs/PACKS.md), explains each step in more depth.

## Start

```sh
npm install
npx playwright install chromium   # once, for npm run docs
npm test                          # the pack's tests, in jsdom
npm run lint                      # its rules against core's lint rules
npm run docs                      # docs/RULE_CATALOG.md, and the examples run in Chromium
```

## What is here

| File | What it is |
|---|---|
| `index.js` | The pack: its name, namespace, rules, profiles, checklist items and messages. |
| `rules/automatic/__NAMESPACE__-link-text-specific.js` | A rule of its own that decides: links named only "click here" or "read more" fail. Uses core's helpers to find links and compute their names. |
| `rules/automatic/__NAMESPACE__-contrast-enhanced.js` | A variant of core's `contrast-minimum`: the same code at 7:1 instead of 4.5:1, with no code of its own. |
| `rules/manual/__NAMESPACE__-new-window-review.js` | A manual rule: it never fails, and asks a person to check each link that opens a new window. |
| `i18n/en.json` | The rules' messages in English. |
| `tests/rules/*.test.js` | A test per rule. |
| `tests/profiles.test.js` | What each profile runs, and the checklist's items. |
| `docs/RULE_EXAMPLES.md` | Examples of each rule's outcomes, checked by `npm run docs`. |
| `eslint.config.js` | Core's lint rules for rules (`@surea11y/core/eslint-plugin`). |

## The profiles: which rules run

A scan runs the pack's rules only under one of its profiles (or when it asks for a rule by id). Each profile in `index.js` says what runs:

- `tags`: the rules carrying any of these tags. `wcagTags('2.2', ['A', 'AA'])` gives the tags of core's WCAG 2.2 A and AA rules. The pack's namespace tag, `__NAMESPACE__`, is always added, so the pack's own rules run under every profile.
- `rules`: rules added by id, core's or the pack's, such as core's best-practice rules (`region`, `heading-order`), which no WCAG tag selects. With `tags: []`, the profile runs exactly these and the pack's own.
- `exclude: { rules, criteria }`: rules left out, or WCAG criteria waived (their rules and rollups go).
- `severity`: another severity for a rule under the profile. Results show it, and keep the rule's own as `ruleSeverity`.

As generated:

| Profile | Runs |
|---|---|
| `__NAMESPACE__-policy` | Core's WCAG 2.2 A and AA rules, `region` and `heading-order`, and the pack's rules; not core's `contrast-minimum` (the 7:1 variant replaces it); `img-alt-present` is critical. |
| `__NAMESPACE__-quick` | Exactly `img-alt-present`, `link-name-present`, `page-title-present` and the pack's rules. |

Core's rules, with their ids, tags and what each checks, are in core's [`docs/RULE_CATALOG.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_CATALOG.md). After `npm run docs`, this pack's `docs/RULE_CATALOG.md` lists its rules, profiles and items.

## The checklist's items

`rollups` in `index.js` are the items: each groups rules, core's or the pack's, into one result (its id starts with the namespace). An item fails when one of its rules fails, asks (`cantTell`) when one asks, and passes when they pass. Under a profile, results list the items in `rulesResults`, the HTML report shows them under the checklist's title, SARIF tags each rule with the items it belongs to, and JUnit lists them as properties of each rule's criterion.

## Add a rule

1. Copy the rule closest to what you need, in `rules/automatic/` (it can fail) or `rules/manual/` (it asks a person). Name the file and the `id` `__NAMESPACE__-<what it checks>`.
2. Write its header: `@applicability` (what it applies to), `@expectation` (what it checks), `@reports` (what a finding carries). `npm run docs` puts them in the catalog.
3. Write `runInPage(ctx)`. It runs in the page, so it uses only `ctx`: `ctx.document`, and `ctx.helpers` for core's helpers ([`docs/RULE_HELPERS.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_HELPERS.md)). Read DOM properties through `ctx.helpers.dom` (`npm run lint` says where). Return `pass`, `fail` (automatic rules), `cantTell` or `notApplicable`, with an occurrence per element from `helpers.reportOccurrence`.
   - For core's rule at other thresholds, write a variant instead: `from` names the core rule, `config` its settings.
4. Give it the `__NAMESPACE__` tag, list it in `rules` in `index.js`, and put it in a profile or an item.
5. Add its messages to `i18n/en.json`: the keys in its `meta.i18n` and its occurrences' `i18n`.
6. Add a test in `tests/rules/` and examples in `docs/RULE_EXAMPLES.md`, then run `npm test`, `npm run lint` and `npm run docs`.

Core's [`docs/RULE_AUTHORING.md`](https://github.com/SureA11y/core/blob/main/docs/RULE_AUTHORING.md) describes a rule's fields and outcomes in full.

## Another language

Add `i18n/<locale>.json` with the same keys, and list it in `dictionaries` in `index.js` (`{ en: require('./i18n/en.json'), fr: require('./i18n/fr.json') }`). A scan with `engineOptions.locale: 'fr'` shows them; a locale with no dictionary shows English.

## Use it

In Node:

```js
const { runDomRulesInPage } = require('@surea11y/core');
const policy = require('__PACKAGE__');

const result = runDomRulesInPage(url, null, { packs: [policy], profile: '__NAMESPACE__-policy' });
```

From the command line: `surea11y scan <url> --pack __PACKAGE__ --profile __NAMESPACE__-policy`.

With a browser binding (Playwright, Puppeteer, Selenium, WebdriverIO), which registers the pack in the page for you:

```js
const result = await new A11yCoreBuilder({ page })
  .withPacks(policy)
  .options({ profile: '__NAMESPACE__-policy' })
  .analyze();
```

In Cypress, `withPacks()` takes the module name (`'__PACKAGE__'`) and the binding's plugin prepares it in Node. In a page of your own, inject `packScript([policy])` from `@surea11y/core/pack` after core's browser bundle and name the pack in `engineOptions.packs` as `__PACKAGE__@<version>`. See "Packs" in core's [`docs/ENGINE_OPTIONS.md`](https://github.com/SureA11y/core/blob/main/docs/ENGINE_OPTIONS.md#packs--rules-and-standards-from-outside-core).

## Publish

The package is `private`. Choose its licence, set `license` and remove `private` in `package.json`, and run `npm publish`. `core` in `index.js` says which core versions it works with; a scan with another core skips the pack and says why in `skippedPacks`.
